### R-01: Date Projections Confuse Symbols With Column Names

**Status: DONE 2026-09-05.** The defect and reproduction below describe the reviewed baseline;
the resolution and fresh validation follow them.

**Baseline locations:** `src/dev/brikk/trino/doris/RewriteDateProjections.kt:61-68,104-116,142-146`.

Both date rules render `quote(source.name)` directly. A connector-expression variable name
is a planner symbol, not necessarily the physical Doris column name. Trino sanitizes names,
strips numeric suffixes, and allocates distinct symbols; the authoritative correspondence
is in the rewrite context's assignments.

**Live reproduction:** a table had `dt_6 = '2020-01-02 03:04:05'` and
`dt = '2030-06-07 08:09:10'`. With ordinary pushdown:

| Query | Pushed | Pushdown Disabled |
|---|---|---|
| `SELECT date(dt_6) FROM t` | `2030-06-07` | `2020-01-02` |
| `SELECT date_trunc('day', dt_6) FROM t` | `2030-06-07 00:00:00` | `2020-01-02 00:00:00` |

The rule silently reads `dt`. If no such physical column exists, the same defect can fail
the query instead. Renamed join outputs and unusual identifiers broaden the exposure.

**Fix direction:** rewrite the variable through `context.rewriteExpression(source)` and
carry its parameters. This also reuses the scalar leaf's native-type validation rather
than treating a TIMESTAMP-typed symbol as proof of native DATETIME metadata.

**Regression requirement:** deliberately different symbol/column names, numeric-suffix
identifiers, quoted identifiers, and date projections over renamed join outputs.
At the review baseline, `TestDorisP6DateProjection.kt:58-72` used uncomplicated `dt0/dt3/dt6` names.

**Resolution:** `RewriteCastDatetimeToDate` and `RewriteDateTrunc` now obtain the input SQL
from `context.rewriteExpression(source)` and preserve its parameter list. The existing scalar
rewriter resolves physical/synthetic column assignments, quotes names, and validates native
mapping compatibility. A rejected source leaves the projection local. The obsolete quote
constructor arguments were removed from the rules and their registration in `DorisClient`.
The admitted date functions, units, source shapes, and result type handles are unchanged.

**Regression evidence:** all three new `TestDorisDateProjectionRules` tests and both new
live tests failed before the production fix. The live baseline returned 2030/2031 dates
instead of 2020/NULL, and the pushed join failed with `Unknown column 'dt'`. They now pass.
Unit coverage includes distinct planner/physical names, reserved/spaced/backtick names,
synthetic columns, incompatible native metadata, and parameter preservation. Live coverage
in `testDateProjectionsResolvePhysicalColumnNames` and
`testDateProjectionsResolvePushedJoinColumns` checks result equivalence, fully pushed plans,
grouping, NULLs, and audit SQL referencing actual physical/generated join-column names.

**Fresh verification:** 60 tests across nine selected suites passed, with zero failures or
skips; detekt and plugin assembly verification also passed (79 jars). Command:

```bash

  --tests '*TestDorisDateProjectionRules' \
  --tests '*TestDorisP6DateProjection' \
  --tests '*TestDorisScalarVariable' \
  --tests '*TestDorisB1ScalarPushdown' \
  --tests '*TestDorisP5JoinPushdown' \
  --tests '*TestDorisTemporalRange' \
  --tests '*TestDorisTemporalRangeMapping' \
  --tests '*TestDorisTimezoneAudit' \
  --tests '*TestDorisPushdownEvidenceDrift' \
  detekt verifyPluginAssembly
```

### R-02: JSON Subscript Syntax Is Not Semantic Equivalence

**Status: DONE 2026-09-05.** The defect and reproduction below describe the reviewed baseline;
the resolution and fresh validation follow them.

**Baseline locations:** `src/dev/brikk/trino/doris/RewriteJsonExtractScalarEquality.kt:85-94,111-118,142-143`.

`SIMPLE_PATH` permits array subscripts without checking the runtime JSON shape. Doris
treats `[0]` on a non-array as an identity step. Trino does not do that for a scalar;
Trino also allows numeric path tokens to select numeric object-field names where Doris
interprets a subscript differently. The existing output-literal guards cannot repair traversal.

**Live reproduction:** the table contained row 1 with `{"a":"x"}` and row 2 with
`{"a":{"1":"x"}}`.

| Predicate | Pushed IDs | Pushdown-Disabled IDs |
|---|---|---|
| `json_extract_scalar(doc, '$.a[0]') = 'x'` | `[1]` | `[]` |
| `json_extract_scalar(doc, '$.a[1]') = 'x'` | `[]` | `[2]` |

**Fix direction:** keep subscript-bearing paths local until a shape-aware rewrite preserves
Trino traversal. Rejecting only `[0]` does not address numeric object keys.

**Regression requirement:** scalar, object, array, missing, and JSON-null intermediates;
numeric object keys; zero and nonzero subscripts. At the review baseline, the correctly
shaped array cases in `TestDorisP5Batch.kt:68-74` did not cover this boundary.

**Resolution:** the rule's path allowlist now accepts only one or more simple dotted field
names (`$.a`, `$.a.b`). Every subscript-bearing path stays local, including root, nonzero,
and nested subscripts, in either equality orientation. No data-shape assumptions or new
remote translation were introduced. The existing equality/literal guards and parameter
binding are unchanged. The README, rule/evidence comments, and P5 notes now state the
narrower contract; historical probe conclusions are explicitly qualified rather than erased.

**Regression evidence:** the new unit subscript-rejection test and three new live tests
failed before the production fix. On the new fixture, `$.a[0] = 'x'` returned IDs `[1,4]`
instead of `[3,4]`; `$.a[1] = 'x'` returned `[5,11]` instead of `[2,5,11]`; the mixed-predicate
plan lacked its required local filter. All now pass. The new dotted-path unit and live
controls passed both before and after the fix.

`TestDorisJsonExtractScalarEquality` checks actual rewrite admission in both orientations,
SQL rendering, and parameter order. The new `TestDorisP5Batch` cases use a separate 23-row
fixture covering scalar/object/array intermediates, numeric object keys, root and nested
subscripts, empty arrays, missing fields, SQL NULL, and JSON null. They compare explicit
expected IDs with pushdown-disabled evaluation and require retained Filter nodes. An audit
check proves that `id >= 3` still pushes while the unsafe JSON expression does not. The old
correctly shaped `$.arr2[1]` case now expects local evaluation, preserving its result.

**Fresh verification:** 37 tests across five selected suites passed, with zero failures or
skips; detekt and plugin assembly verification also passed (79 jars). Command:

```bash

  --tests '*TestDorisJsonExtractScalarEquality' \
  --tests '*TestDorisP5Batch' \
  --tests '*TestDorisP3Composition' \
  --tests '*TestDorisTimezoneAudit' \
  --tests '*TestDorisPushdownEvidenceDrift' \
  detekt verifyPluginAssembly
```

This was scoped validation, not a new full-suite, multi-FE, or packaged-server smoke run.
R-01's prior changes remain intact; this follow-up closes only R-02.

### R-03: Textualized Complex Columns Regain Native Semantics

**Status: DONE 2026-09-05.** The defect and reproduction below describe the reviewed baseline;
the resolution and fresh validation follow them.

**Baseline locations:** `src/dev/brikk/trino/doris/DorisClient.kt:498-510,528-530,641-647`;
mapping contract at `DorisTypeMapping.kt:222-229`.

Unsupported ARRAY/MAP/STRUCT columns can be exposed as VARCHAR renderings. The mapping
disables predicate pushdown, and E-02 now protects scalar leaves. However, grouping and
TopN have independent gates: they accept VARCHAR and exclude Decimal256 specifically,
without requiring native string metadata.

**Live grouping/DISTINCT reproduction:** the existing `p2_array.strs` fixture contains two
different arrays, one element `a", "b` versus two elements `a` and `b`. Both are exposed as
the same text, `["a", "b"]`.

```sql
SET SESSION doris.unsupported_type_handling = 'CONVERT_TO_VARCHAR';
SELECT a_vc, count(*) FROM doris.p2_array.strs GROUP BY a_vc;
SELECT DISTINCT a_vc FROM doris.p2_array.strs;
```

Remote grouping returned two identically rendered groups, each with count 1; local grouping
returned one group with count 2. Remote DISTINCT returned the same exposed value twice;
local DISTINCT returned it once. This is not merely a violated plan preference.

**Live TopN reproduction:** for a converted `ARRAY<VARCHAR>` containing `[]` and `["x"]`,
with `string_pushdown_mode=BINARY`, `ORDER BY a LIMIT 1` returned `[]`. Trino VARCHAR
ordering returned `["x"]`. The guaranteed TopN removes the opportunity for local correction.

**Fix direction:** validate native provenance at grouping and sort-key admission, as the
scalar leaf already does. For VARCHAR, admit actual `varchar/string/text`, not arbitrary
remote types rendered as strings. Preserve valid synthetic native-string handles.

**Regression requirement:** use the existing ambiguity fixture for GROUP BY, DISTINCT,
and decomposed count-distinct; test converted complex types with selective TopN limits.
ARRAY is proven here; do not generalize an unmeasured specific ordering result to every
MAP/STRUCT implementation, although the missing type gate applies to those handles too.

**Resolution:** `DorisClient` now shares an `isNativeVarchar` check between grouping and
TopN eligibility. It requires both Trino VARCHAR and authoritative JDBC type-name metadata
whose parsed native base is `varchar`, `string`, or `text`. Converted ARRAY/MAP/STRUCT keys,
unknown types, and missing metadata cannot inherit native string grouping/sorting semantics.
The existing Decimal256 guard remains in place. Native string grouping remains eligible in
all string modes, while native string TopN still requires BINARY/FULL. Non-text key rules,
IP TopN, and valid synthetic string-column handles are unchanged. The README now makes the
native-string requirement explicit.

**Regression evidence:** two new unit tests and five new live tests failed before the fix.
The live ambiguity fixture reproduced two groups of count 1 instead of one group of count 2,
duplicate DISTINCT values, `count(DISTINCT)=2` instead of 1, and TopN returning `[]` instead
of `["x"]`. The MAP/STRUCT test exposed missing local aggregation in the old plan. The new
native/synthetic unit control and native/derived live control passed before and after.

`TestDorisStringKeyPushdown` calls the actual client's gates, covering converted types,
Decimal256, unknown/missing metadata, native and synthetic string handles, mixed key orders,
multiple grouping sets, and empty grouping keys. `TestDorisP2aArray` reuses the existing
non-injective string-array fixture for GROUP BY, DISTINCT, count-distinct, and count over
DISTINCT. A four-row fixture tests selective TopN limits with all four NULL orderings across
all four string modes against pushdown-disabled execution. MAP/STRUCT checks require local
aggregation/TopN and compare with local evaluation. Native VARCHAR/STRING, `lower`, and
`coalesce` controls retain eligible pushdown, and text-mapped payloads still pass through
integer-key TopN and integer-key grouping with `count(payload)`.

**Fresh verification:** 119 tests across ten selected suites passed, with zero failures or
skips; detekt and plugin assembly verification also passed (79 jars). Command:

```bash

  --tests '*TestDorisStringKeyPushdown' \
```

### R-04: Outer Joins Break Aggregate Nullability Provenance

**Locations:** `src/dev/brikk/trino/doris/DorisAggregatePushdownRules.kt:291-320`;
join path at `DorisClient.kt:261-276`.

The `min_by`/`max_by` guard correctly recognizes that Doris skips NULL payload rows while
Trino can select a NULL payload. It relies on `JdbcColumnHandle.isNullable == false`.
Trino 483's synthetic join-column creation copies the original column handle, preserving
the base table's NOT NULL flag even on the null-supplying side of an outer join.

**Live reproduction:** `l(id)` contained 1 and 2; `r(id, v NOT NULL)` contained `(2, 60)`.
With `join_pushdown_enabled=true` and strategy `EAGER`:

```sql
SELECT min_by(r.v, l.id)
FROM l LEFT JOIN r ON l.id = r.id;
```

The pushed result was `60`; the local result was NULL. The joined inputs are `(NULL, 1)`
and `(60, 2)`, despite the base payload column being NOT NULL.

**Fix direction:** track effective output nullability through joins, or conservatively
decline these aggregates where the NOT NULL provenance is not established. Do not globally
disable valid base-table `min_by` just to avoid addressing the composition boundary.

**Regression requirement:** LEFT and RIGHT joins feeding both aggregates, unmatched rows
winning the key comparison, and matched-only controls. Current join composition coverage
at `TestDorisP5JoinPushdown.kt:166-178` exercises `count(*)`, which cannot reveal this bug.

### R-05: HA Proxy Abort Is Not A Lock-Free Socket Fallback

**Locations:** `src/dev/brikk/trino/doris/DorisPreparedStatement.kt:65-85,95-101`;
normal connection construction at `DorisClientModule.kt:112-115`.

The wrapper synchronously calls `connection.abort(directExecutor())`. For comma-list,
load-balancing, or replication URLs, the connection can be Connector/J's HA proxy rather
than a physical connection. Connector/J 9.7.0's `MultiHostConnectionProxy` takes its lock
before processing `abort`; statement execution holds that same lock.

**Live reproduction:** the production `DorisPreparedStatement` wrapped a normal comma-list
connection to the test FE, executing `SELECT sleep(4)`. Its helper callback was deliberately
a no-op, representing the disabled/unavailable helper fallback. After the statement became
visible in processlist, `cancel()` took **4,012 ms**, waiting for execution instead of
interrupting it. This used two entries for the same FE; it proves the driver-proxy locking
problem, not cross-FE routing behavior.

If the helper succeeds promptly, its remote kill can release the lock. If it is disabled,
rejected, expired, or cannot kill the query, the promised independent socket fallback is
blocked. Cleanup also waits uninterruptibly for cancellation completion.

**Fix direction:** capture a verified physical abort target before execution, or otherwise
provide an independently proven non-blocking abort path. Unwrapping during cancellation
can encounter the same busy proxy and is not sufficient by itself.

**Regression requirement:** real HA-proxy execute-phase cancellation with the helper
disabled and failing, plus streaming and concurrent-close paths. Fake immediate-abort
connections and single-host live tests do not prove the HA case.

### R-06: Development Services Are Not Loopback-Only

**Locations:** `compose/docker-compose.yml:28-30`;
`compose/multi-fe/docker-compose.yml:54-56,78-80,99-101`;
`compose/trino/docker-compose.yml:16-19`.

Port mappings such as `9130:9030` publish on all host interfaces. The Doris development
account is root with no password. The manual Trino sandbox is unauthenticated HTTP and
supports dynamic catalogs; its instructions also encourage adding real remote credentials.
A private Docker subnet does not make published host ports private.

This is an unsafe default when the host is reachable by untrusted peers, not a demonstrated
production connector authorization bypass. Actual remote accessibility depends on Docker,
host firewall, and network policy. The manual sandbox documents LAN access intentionally;
that should be an explicit opt-in rather than the default.

**Fix direction:** bind development ports to `127.0.0.1` by default; document authenticated
or explicitly shared overrides. Avoid putting production credentials into an unauthenticated
shared sandbox.

### R-07: Explicit LIKE Escapes Need A Doris Character Gate

**Location:** `src/dev/brikk/trino/doris/RewriteStringLike.kt:85-95`.

The three-argument rule rejects NUL but otherwise passes the escape through. Trino accepts
a single non-ASCII character such as U+00E9; Doris 4.1.3 requires a single ASCII escape.

**Live reproduction:** with `v='a_b'`, the valid Trino predicate
`v LIKE '%\u00e9_%' ESCAPE '\u00e9'`, where each `\u00e9` denotes the actual U+00E9 character,
matched locally. In BINARY mode the remote query failed with
`like escape character must be a single ascii character`.

**Fix direction:** keep unsupported escapes local, or translate the pattern into a
validated Doris escape convention. Add a non-ASCII case beside the current ASCII `!` test.

### R-08: The Statistics Switch Is Below Its Cache

**Locations:** `src/dev/brikk/trino/doris/DorisClient.kt:331-345`;
`DorisSessionProperties.kt:55-59`; Trino 483 `CachingJdbcClient` statistics cache.

The session switch is checked only in the delegate. The upstream cache is keyed by table
handle rather than this session property and returns hits without invoking the delegate.

**Live reproduction:** create a catalog with `metadata.statistics.cache-ttl=5m`, analyze a
one-row table, and run `SHOW STATS`. A subsequent session with
`statistics_enabled=false` still received row count 1 and the same known column statistics.
With caching of missing values enabled, the reverse sequence can also cache unknown
statistics for enabled sessions; that reverse case is source-derived, not live-probed here.

Default zero cross-query TTL avoids this specific exposure. The effect is optimizer and
diagnostic behavior, not a wrong table value.

**Fix direction:** enforce the switch above caching, or include the relevant setting in
cache identity. Test both directions with positive TTL and missing-value caching.

## Strengths

### Architecture And Safety

- **S-01: Appropriate architecture.** The Base JDBC extension is an appropriate scope choice. Doris owns distributed execution;
  the connector translates and streams rather than inventing its own distributed scan engine.
- **S-02: Layered read-only enforcement.** Read-only behavior is layered: access control, explicit JDBC mutator rejection, denial of
  the actual `system.execute` connection entry point, absence of arbitrary-query registration,
  and SELECT-only account tests. This is materially stronger than a README promise.
- **S-03: Safe composition tiers.** Predicate-only ARRAY/JSON rewrites are separated from value-safe composition. That prevents
  a WHERE-equivalent expression from casually becoming unsafe under NOT/AND/OR.
- **S-04: SQL construction.** Query values are generally bound parameters; the inline date-trunc unit comes from a closed
  allowlist, identifiers are quoted, and QueryIds are validated before kill SQL is generated.
  This is a sound SQL-construction posture despite the column-identity bug in R-01.

### Type And Semantic Discipline

- **S-05: Authoritative metadata.** Reading authoritative `information_schema.columns.COLUMN_TYPE` avoids known lossy JDBC
  metadata. Exact integer/decimal paths use exact arithmetic and explicit range checks.
- **S-06: Honest array decoding.** The project refuses native string-array decoding after demonstrating that the wire format
  is non-injective. That is the correct engineering decision; R-03 is a missing downstream
  consequence of that decision, not a reason to guess at decoding.
- **S-07: Temporal discipline.** Temporal handling avoids zone-shifting `getTimestamp` behavior, preserves zoneless values,
  and tests year zero, negative epochs, precision, upper boundaries, and multiple zones.
- **S-08: Evidence-based aggregate gates.** Aggregate exclusions reflect measured overflow, rounding, NULL, and floating-point
  differences. Opt-in approximate pushdown honestly states that estimates can differ.
- **S-09: Substantive prior fixes.** Recent E-01/E-02/E-06 fixes are substantive: disabled Decimal256 value semantics, native
  scalar-leaf validation, and guards on original temporal domain endpoints before compaction.

### Tests And Operations

- **S-10: Adversarial live tests.** Live result differentials, plan assertions, audit SQL, independent element/size oracles,
  and inverted-index evidence test more than generated SQL strings. Many tests are genuinely
  adversarial rather than happy-path demonstrations.
- **S-11: Lifecycle coverage.** Cancellation lifecycle tests now exercise real `JdbcPageSource` seams and controlled races,
  not just a stand-alone copy of the helper loop. Per-statement UUIDs address sibling isolation.
- **S-12: Bounded helper resources.** Bounded helper concurrency, queue deadlines, short network timeouts, and cleanup watchdogs
  are substantial improvements. Their limitations are mostly documented honestly.
- **S-13: Assembly safeguards.** The assembly guard treats Trino's parent-first classloading boundary seriously, including
  ServiceLoader registration that programmatic plugin installation would otherwise miss.
- **S-14: Useful historical evidence.** Probe reports preserve rejected alternatives and why they were rejected. That makes future
  Trino/Doris upgrades easier to review than uncommented allowlists would.

## Weaknesses And Quality

### Q-01: Correctness Is Too Local

The recurring weakness is **loss of provenance at boundaries**:

| Boundary | Lost Fact | Consequence |
|---|---|---|
| Planner variable to generated SQL | Physical column identity | R-01 |
| Accepted JSON path syntax to runtime document traversal | Intermediate value shape | R-02 |
| Remote complex type to exposed VARCHAR | Native type versus textual rendering | R-03 |
| Base table to outer-join result | Effective nullability | R-04 |
| Physical JDBC connection to HA proxy | Lock behavior of abort | R-05 |
| Session policy to shared statistics cache | Per-session enablement | R-08 |

This does not call for a large new abstraction framework. Prefer small common admission
checks where the same invariant is genuinely shared, and explicit validation at the
operation that relies on it. A Trino type alone is not enough to establish remote semantics.

**Q-02: Cross-feature regression matrix.** The strongest next testing investment is a composition matrix: converted type plus
GROUP BY/TopN; projection plus renamed columns; outer join plus NULL-sensitive aggregate;
session switch plus cache hit; cancellation plus HA proxy plus helper failure. Adding more
ordinary values to already-tested isolated functions will not find these classes of bugs.

### E-16: Evidence Prose Exceeds Evidence Enforcement

`DorisPushdownEvidence` performs real registry tuple/provenance checks. Its rendering
substring tests, however, inspect handwritten documentation rather than rule output, and
test-class existence is not proof that the advertised guard is exercised. Assertions such
as "one entry per rule" and "structural proof" overstate this mechanism.

Keep the evidence index, but describe it as an artifact-drift check and a map to proof.
Where feasible, test actual rewrite output and rejection behavior. Avoid adding more
handwritten proof-shaped metadata that can drift independently of the implementation.

**D-06: Current-code comment accuracy.** The volume of historical comments is itself a maintenance cost. Date-stamped reports are
valuable; current-path KDoc that still says "until P2", "unproven", or "forced OFF" after
the behavior changed is not. Explain present invariants near code and link historical detail.

### Kotlin And API Quality

**Q-03: Readability assessment.** The code is generally readable, typed, and reasonably decomposed. It is not suffering from
a broad readability or formatting crisis. The highest-value cleanup is targeted:

- **E-24: Targeted deduplication.** Share duplicated operator/dialect/type checks when that prevents admission-policy drift.
  Do not merge scalar and value-safe rewriter holders merely because their shapes resemble
  each other; their separation encodes a safety boundary.
- **E-25: API-shape cleanup.** Replace nullable `Optional` return shapes and side-effect-only rejection helpers when
  touching those functions. Remove the unused scalar-projection constructor dependency.
- **E-25: Defensive engine-shape checks.** Harden unchecked assignment casts and malformed-expression arity handling where a cheap
  rejection preserves the fail-closed contract. Normal Trino-generated shapes are not shown
  to violate these assumptions today.
- **Q-04: Strict parser contracts.** Tighten type/wire parser grammar if "strict" remains its documented contract. Java float
  parsers accept forms outside the described wire grammar; IPv4 array decoding does not
  independently reject a genuine IPv6 value for an IPv4 descriptor. These are malformed-input
  hardening issues, not demonstrated valid-Doris data corruption. Coordinate metadata-parser
  work with E-10/E-25/E-33; the wire-decoder grammar is an additional part of Q-04.
- **Q-05: Legacy join SPI upgrade debt.** Track the deprecated legacy join SPI as upgrade debt. The fresh compiler warnings are
  informative; suppressing them without an upgrade plan would not improve compatibility.

### Reliability, Scale, And Observability

**Q-06: Scan throughput tradeoff.** One remote statement per scan and streaming reads are deliberate, sensible constraints.
They also mean that a single Trino scan does not gain parallel fetch bandwidth by splitting
the Doris relation. That is a throughput tradeoff, not automatically a defect.

**Q-07: Metadata cost and scaling.** Metadata listing can involve many per-table calls; statistics adds remote work and accepts
advisory snapshots with different ages. After inserts/deletes or partial analysis, mixed
nonzero counts/NDV/null fractions may still be stale despite E-08/E-09. No benchmark or
freshness guarantee should be inferred from the existing small correctness fixtures. Measure
metadata/statistics round trips before optimizing; stale-estimate handling is tracked as K-02.

**Q-08: Operational cancellation metrics.** Cancellation counters are useful to tests but mostly internal/static; failures commonly
surface only at DEBUG. Expose actionable queue/expiry/timeout metrics before relying on
best-effort behavior at scale. Ordinary/helper connection-deadline limitations are separate
items K-04/K-05, not implied to be solved by exposing metrics.

### Test And Release Quality

**E-30: Live-test developer experience.** The live suite is valuable but expensive and coupled to a root account, exact port, container
name, and mutable fixtures. Prefer an explicit unit/live separation with a single clear
preflight diagnostic. Do not silently skip required CI integration tests when Doris is down.
Endpoint configurability should follow, not precede, the destructive-target safeguards.

**E-29: Cancellation validation lanes.** Default CI now includes meaningful production cancellation coverage. It still omits the
slow tagged suite and the multi-FE overlay, and a default-suite trace-id probe failed in this
review. A scheduled explicit integration lane would close an important coverage gap.

**Q-09: Packaged-plugin smoke gate.** Add a packaged-directory real-Trino load/catalog/query
smoke to CI/release validation; filename/ServiceLoader checks and in-process tests do not
exercise the same isolated plugin classloader. This is the smoke-test part of E-32.

**Q-10: Independent IP TopN oracle.** The IP TopN test needs an independent oracle: its local helper disables expression translation,
not TopN; its LIMIT exceeds the fixture cardinality; its full-pushdown result comparison is
unordered. The upstream assertion still supplies useful disabled-pushdown result-set checking,
so "there is no differential coverage" would be unfair. What is missing is an ordered,
selective-limit comparison (`TestDorisIpPushdown.kt:41-43,102-108`).

## Residual Risks

These are limitations or hypotheses, not additional confirmed wrong-answer findings:

- **K-01: Floating-point wire fidelity.** FLOAT/DOUBLE wire text can already lose finite precision or render stored finite extrema
  as infinity. The mapper now reads that text without the previous infinity crash; it cannot
  recover information the wire discarded. Local evaluation is therefore not necessarily
  stored-value fidelity. Avoid "value-exact" claims for these mappings/array elements.
- **K-02: Mixed-age statistics.** Statistics can combine differently aged nonzero records.
  Establish realistic freshness expectations and stale-snapshot tests before claiming exact estimates.
- **K-03: Malformed statistics isolation.** Malformed NaN/infinite count fields deserve
  defensive rejection rather than allowing one bad record to discard
  healthy estimates through the outer fail-soft catch.
- **K-04: Helper pre-connect stalls.** DNS, credentials, custom socket/authentication code, and remote TLS-store loading can stall
  before the helper's post-connect watchdog is installed. The current notes acknowledge
  this; do not claim an absolute setup wall-clock deadline.
- **K-05: Ordinary connection setup deadline.** Normal scan connections lack a default
  socket-read timeout before the statement wrapper exists. Establish the operational deadline
  contract and test a silent server greeting separately from helper connection behavior.
- **K-06: Helper identity and permissions.** With per-host credentials or credential rotation, a helper reconnecting through another
  FE may authenticate differently from the original scan. Property-preservation tests are
  not a restricted-account cross-FE cancellation proof. A live identity/permission matrix
  is needed before promoting this to a confirmed defect.
- **K-07: Statement wrapper contract boundary.** `DorisPreparedStatement` protects the no-argument scan `executeQuery()` path. Other
  delegated execution methods and vendor unwraps are outside that contract. Current Trino
  scans use the protected seam; no current SQL-user escape was identified through this fact.
- **K-08: Arbitrary-query entry-point drift.** Read-only tests should explicitly pin the absence of an arbitrary `query()` table function
  during Trino upgrades. Reflection allowlists and unavailable entry points are a different
  defense from rejecting arbitrary SQL at every possible internal method.
- **K-09: Cancellation versus resource reclamation.** FE cancellation-log evidence establishes cancellation processing, not independently that
  every BE resource has been reclaimed. Keep those operational claims distinct.
- **K-10: Unicode and version drift.** Unicode case mapping has a substantial adversary battery, not exhaustive proof across
  Unicode versions and malformed stored bytes. Re-probe when upgrading Doris/Trino/runtime
  dependencies; the startup registry does not dynamically establish server-version equivalence.

## Q-11: Overall Judgment

This is serious connector engineering, not a thin MySQL rename: the type work, measured
semantic exclusions, read-only layering, and live-oracle infrastructure are clear strengths.
The repository has already demonstrated that it can investigate and fix difficult boundary
bugs rather than papering over them.

The present weakness is that the confidence language is ahead of the composition guarantees.
Several individually sensible gates become unsafe when metadata is renamed, textualized,
null-extended, cached, or proxied. The fresh probes found wrong answers in small valid inputs,
including default-mode queries, so another feature push would be the wrong next investment.

My recommendation is a focused correctness-hardening pass, not a rewrite. Keep the design,
reduce duplicated semantic admission logic, test the boundaries between features, and make
current claims match what the executable evidence actually establishes.
